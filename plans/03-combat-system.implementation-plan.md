# Боевая система (оружие, урон, враг)

## Что делаем

Три этапа, каждый — рабочее и проверяемое состояние игры:

1. **Оружие + односторонний бой.** Первое оружие — нож (ближний бой). Новая сущность `Enemy` — гуманоид, стоит на месте, без защиты, только получает урон. Игрок атакует кликом.
2. **Враг атакует в ответ.** Enemy находит кратчайший путь к игроку, пересчитывает путь каждые 1-2 пройденные клетки, идёт к игроку, входит в радиус поражения ножа — бьёт. Бой идёт до смерти одной из сторон.
3. **Вне рамок этого плана** (явно не входит сейчас): защита/уклонение, стрелковое/взрывное оружие, UI полосок здоровья над головой — добавляется отдельными итерациями после проверки этапов 1-2. Но архитектура оружия (раздел 1) закладывается так, чтобы эти типы добавлялись новыми модулями, а не переписыванием существующего.

### Заявленное направление будущего расширения (не реализуем сейчас, только учитываем в архитектуре)

- Холодное оружие нескольких видов урона: колющее, режущее, дробящее (нож/меч/дубинка) — разные категории урона, но одна и та же механика «мгновенный контакт в радиусе».
- Стрелковое оружие — полёт снаряда (пули) во времени, с анимацией, коллизией по пути, попаданием по факту долёта.
- Взрывное оружие (гранаты) — урон по площади в момент детонации (по контакту или по таймеру взрывателя).
- Комбинированное стрелково-взрывное (гранатомёт/ракета) — снаряд, летящий во времени, при попадании/по таймеру производящий взрыв с уроном по площади.
- Экзотика — не продумываем заранее, архитектура должна допускать добавление новой категории, не более того.

## Текущая архитектура (что есть)

- `Entity` — id/position/sprite/highlight. Общий предок всех сущностей.
- `Character extends Entity` — добавляет `stats` (StatsComponent) и `health` (HealthComponent), тикает здоровье каждый `update`. От него — только `Player`.
- `NPCEntity extends Entity` — отдельная ветка: needs (голод/жажда) + приоритетные AI-поведения + своя система path-follow (`setTargetPosition` → `WorldMap.findPath` → массив waypoint'ов, движение к текущему waypoint). От него — `Wolf`, `Rabbit`. Не трогаем (работающая ветка животных, к бою отношения не имеет).
- `HealthComponent.applyDamage(bodyPartType, amount)` — уже принимает **конкретную** часть тела, сама решает уничтожение/смерть/кровотечение/стат-модификаторы. Готова к использованию боевой системой без изменений.
- `HUMANOID_BODY_PLAN` (`health/body-plans/humanoid.ts`) — самодостаточная таблица частей тела (тип, родитель, здоровье, vital, кровотечение).
- `WorldQuery.findNearestEntity(position, radius, predicate)` — уже есть, ищет ближайшую сущность по фильтру в радиусе. Годится и для поиска цели атаки.
- `WorldMap.findPath(start, end)` — BFS-путь по клеткам, уже используется животными.
- Сгенерированный спрайт гуманоида (`humanoid-sprite-generator.ts`) — один body type (`MALE`), три позы. Переиспользуем для `Enemy` с тонировкой (`setTint`) для визуального отличия от игрока.

Вывод: `Character` — правильное место для боевого компонента (аналогично stats/health). `Enemy` логичнее делать через `Character`, а не `NPCEntity` — ему не нужны needs и приоритетные поведения животных, только health/stats/бой + (на этапе 2) простое преследование.

## Подход

### 1. Оружие — данные, разделённые по категории доставки урона

Категории оружия различаются не количеством урона, а **механикой доставки** урона: ближний бой — мгновенная проверка контакта; стрелковое — летящий во времени снаряд с коллизией по пути; взрывное — урон по площади в момент детонации; комбинированное — снаряд, который долетает и взрывается. Это разные алгоритмы, поэтому закладываем их как разные варианты данных с общим корнем, а не как универсальную «плоскую» структуру с кучей необязательных полей:

- `WeaponCategory` enum — `MELEE` (реализуем сейчас), плюс зарезервированные на будущее `RANGED`, `EXPLOSIVE`, `RANGED_EXPLOSIVE` (добавляются как новые варианты, когда до них дойдёт очередь — не создаём их заранее пустыми).
- Определение оружия — discriminated union по `category`: `MeleeWeaponDefinition` (урон, радиус поражения в клетках, кулдаун, список `attackMoves`). Будущие `RangedWeaponDefinition`/`ExplosiveWeaponDefinition` получат свои специфичные поля (скорость снаряда, радиус взрыва и т.п.), не трогая `MeleeWeaponDefinition`.
- `attackMoves: MeleeAttackMove[]` — каждый возможный удар оружия описан отдельной записью: `WeaponDamageType` (`PIERCING`/`SLASHING`/`BLUNT` — колющее/режущее/дробящее) + тип анимации удара (см. п.8). При каждой атаке случайно выбирается один элемент списка — он одновременно определяет и тип урона, и какая анимация проигрывается. `WeaponDamageType` сейчас — чисто описательное поле, без игровых последствий: задел на будущее — по аналогии с `injury-effect-rules.ts` позже можно завести таблицу «тип урона → эффект» (кровотечение от режущего, оглушение от дробящего, бронепробитие от колющего), не меняя сами определения оружия.
- Первая и пока единственная запись в таблице — нож (`MELEE`), с двумя `attackMoves`: укол (`PIERCING`) и мах (`SLASHING`).

### 2. `CombatComponent` — третий компонент `Character`, атака через резолвер по категории

По аналогии с `stats`/`health`: хранит текущее экипированное оружие и таймер кулдауна. Сама логика «как именно отработать атаку» не хардкодится в компоненте, а делегируется резолверу, выбранному по `category` оружия (простой switch/фабрика по enum) — это и есть точка расширения под будущие типы:

- Резолвер ближнего боя (единственный, что строим сейчас) — то, что описано ниже в п.4/6: мгновенная проверка дистанции + удар.
- Резолверы стрелкового/взрывного оружия — не пишем сейчас. Когда понадобятся, они будут порождать новую сущность `Projectile` (см. п.9), а не расширять `CombatComponent` условиями — старый код резолвера ближнего боя и класс `Character`/`Player`/`Enemy` при этом не меняются.

И `Player`, и `Enemy` получают `CombatComponent` бесплатно через `Character` — симметрично, один и тот же код обслуживает удары в обе стороны.

### 3. Выбор поражаемой части тела

`HUMANOID_BODY_PLAN` — уже самодостаточная таблица, добавляем в неё вес попадания на каждую часть, приблизительно пропорциональный площади части тела (торс — самый большой вес, голова заметно меньше, глаза — совсем маленький). Общая функция «взвешенный случайный выбор части тела по BodyPlan» — используется и игроком, и врагом, живёт рядом с таблицей.

### 4. Игрок атакует (этап 1)

`Player` сейчас не имеет доступа к `EntityManager`/`WorldQuery` (в отличие от `NPCEntity`) — добавляем в конструктор, как у животных. Атака — по клику мыши (когда не зажат Ctrl, чтобы не конфликтовать с существующим выделением сущностей): ищем ближайшего врага в радиусе оружия через `WorldQuery.findNearestEntity`, передаём в `CombatComponent`.

### 5. `Enemy` — новая сущность (этап 1: пассивный)

`Enemy extends Character`, `EntityType.ENEMY`, гуманоидный `BodyPlan` (переиспользуем `HUMANOID_BODY_PLAN`), спрайт — существующая мужская текстура с тонировкой. На этапе 1 никакого AI: стоит на месте, `update` только тикает здоровье (кровотечение/смерть уже отрабатывает `Character`). `MainScene` спавнит одного `Enemy` рядом с игроком для проверки.

### 6. Враг преследует и атакует (этап 2)

В `Enemy` добавляется собственная минимальная логика преследования — отдельная от `NPCEntity` (сознательно не переиспользуем её path-follow, чтобы не трогать рабочую ветку животных): хранит текущий путь и waypoint, при отклонении от последней точки пересчёта на 1-2 клетки — заново вызывает `WorldMap.findPath` до текущей позиции игрока (не по таймеру, как у животных, а по пройденной дистанции — так задал пользователь). При входе в радиус оружия — останавливается, атакует через свой `CombatComponent` (тот же механизм, что и у игрока).

### 7. Смерть и конец боя

Ничего нового изобретать не нужно — `HealthComponent.isDead()` уже есть. `Player.update` уже блокирует движение при смерти (сделано в прошлом плане) — тем же флагом блокируем и атаку. `Enemy` при смерти прекращает AI/атаку и остаётся на месте неподвижным телом (без удаления из мира — это не требуется прямо сейчас).

### 8. Текстура оружия и анимация удара

За основу — RimWorld: оружие рендерится отдельным слоем поверх персонажа, с нужной стороны в зависимости от того, куда персонаж повёрнут; при ударе — короткая анимация, вид которой зависит от `attackMoves`.

- **Текстура.** Не процедурная генерация, а готовый PNG-ассет (`public/assets/sprites/knife.png`, с прозрачным фоном), загружается как обычная текстура — по тому же паттерну, что `rabbit.png`/`wolf.png`. Одна текстура на тип оружия, без разбивки по позам — саму текстуру не меняем, меняем только то, как располагаем и поворачиваем один и тот же спрайт.
- **Крепление к персонажу и 4 положения.** `CombatComponent` (уже владеет текущим экипированным оружием) создаёт при экипировке отдельный `Phaser.GameObjects.Image` для оружия. Оружие поворачивается вместе с телом: подробная таблица всех 4 положений (сторона/ориентация/глубина по каждой из комбинаций `HumanoidPose`+`flipX`) зафиксирована отдельно в [`game.design-doc.md`](../game.design-doc.md) — здесь не дублируем, только ссылаемся. Кратко: точка крепления и ориентация — таблица смещений по позе, глубина — **не константа**, а переключение между двумя значениями рендер-глубины (`RENDER_DEPTH_WEAPON_FRONT` — выше `RENDER_DEPTH_ENTITY_SPRITE`, для положений 1-2; `RENDER_DEPTH_WEAPON_BEHIND` — ниже, для положений 3-4) в зависимости от текущей позы.
- **Наклон при беге не наследуется.** У `Player` спрайт тела при движении крутится (`setRotation` от `HUMANOID_MAX_LEAN_ANGLE`, см. `updateSpriteLean`) — на weapon-спрайт этот поворот **не** переносим, он держит `rotation = 0` (кроме собственного поворота во время `SLASH`-анимации). Вместо наклона — небольшое позиционное смещение по X в сторону направления движения (новая константа амплитуды сдвига), чтобы оружие визуально «держалось в руке», а не висело статичной точкой при беге в стороны.
- **Facing для `Enemy`.** Сейчас `Enemy` не считает позу/направление взгляда (в отличие от `Player`, который выводит его из позиции курсора). Чтобы оружие рисовалось с правильной стороны и у врага, на этапе 2 (когда враг преследует и бьёт) ему нужен свой facing-angle — простейший вариант: направление на игрока в момент атаки, через тот же `resolveHumanoidFacing`.
- **Анимация удара.** В проекте нет спрайт-листов/фреймовой анимации — есть только твины трансформаций (`Phaser.Tweens`, уже используются для наклона спрайта игрока и фокуса камеры). Идём тем же путём: `AttackAnimationType` — `THRUST` (укол: быстрый рывок weapon-спрайта вперёд по направлению взгляда и обратно) и `SLASH` (мах: быстрый поворот weapon-спрайта по дуге в сторону и обратно). Каждый тип — твин с параметрами (амплитуда/угол, длительность) в `const.ts`. Тип анимации приходит из выбранного `attackMoves`-элемента (п.1) — укол проигрывает `THRUST`, мах — `SLASH`.
- **Синхронизация с уроном.** Не усложняем сейчас: урон применяется сразу в момент срабатывания атаки (как и раньше), анимация — чисто визуальное сопровождение поверх кулдауна, без завязки на конкретный кадр. Можно уточнить позже (например, применять урон в середине твина).

### 9. Задел на будущее: сущность `Projectile` (не реализуем сейчас)

Когда дойдёт очередь до стрелкового/взрывного оружия, снаряду понадобится собственная лёгкая сущность — `Projectile extends Entity` (не `Character`: у снаряда нет health/stats, только позиция/скорость/направление и правило срабатывания). Резолвер стрелкового/взрывного оружия (п.2) создаёт `Projectile`, дальше он живёт своим `update` (движение по прямой или дуге, проверка коллизии с `Character` на пути), а по срабатыванию — наносит урон: точечно одной цели (пуля) или по всем `Character` в радиусе взрыва (граната/ракета), тем же `HealthComponent.applyDamage` + взвешенным выбором части тела из п.3. Ни `CombatComponent`, ни `Character`, ни существующий резолвер ближнего боя этим не затрагиваются — только новый файл сущности и новый резолвер.

### 10. Константы

Всё новое — в `const.ts`: урон/радиус/кулдаун ножа, дистанция пересчёта пути врага, цвет тонировки врага и т.п. Веса попадания по частям тела остаются внутри самой таблицы `HUMANOID_BODY_PLAN` (она уже самодостаточная структурированная таблица — не разбиваем на отдельные константы, по тому же принципу, что и остальные поля plan'а).

## Идеи на подумать (не для реализации сейчас)

Руки и ноги отдельно не рендерятся (спрайт — плоская текстура тела), поэтому шаг сейчас никак не читается визуально. На будущее, чисто косметически:

- **Покачивание оружия в такт ходьбе.** Раз руки нет, но оружие в руке — само оружие может циклически покачиваться (небольшое смещение вверх-вниз/вперёд-назад по синусоиде, привязанной к пройденной дистанции, а не ко времени — чтобы на месте оружие не «ходило»), имитируя мах руки при шаге.
- **Лёгкое покачивание торса при ходьбе.** Дополнительно к уже существующему наклону в сторону движения (`updateSpriteLean`) — небольшая колебательная добавка на пару градусов, тоже завязанная на пройденную дистанцию, создающая ощущение шагающей походки.

Оба пункта — чисто визуальная полировка, не влияют на бой/логику, реализуются позже отдельным заходом.
