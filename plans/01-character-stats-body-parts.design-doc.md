# Статы персонажа и части тела (RimWorld-style)

## Что делаем

Подготовительная система под будущее оружие и AI-персонажей:
- Статы персонажа (скорость, дальность обзора, точность стрельбы) — сейчас хардкод, архитектурно готово под влияние скиллов/травм позже.
- Дерево частей тела (голова/мозг/глаза, шея, туловище/сердце, руки, ноги) с здоровьем и последствиями урона.
- Правила смерти: мгновенная (жизненно важный орган), кровотечение (шея/горло), деградация (потеря глаза → хуже обзор).
- Окно персонажа в UI — состояние частей тела текущего игрока.

Оружия и боя пока нет — урон наносится только вручную через debug-кнопки в UI, чтобы систему можно было проверить уже сейчас.

## Текущая архитектура (что есть)

- `Entity` (абстрактный) — id, position, sprite, highlight-рамка. Не знает о здоровье/статах.
- `NPCEntity extends Entity` — needs (голод/жажда) + приоритетные AI-поведения. От него — `Rabbit`, `Wolf`. Не трогаем.
- `Player extends Entity` — прямое управление (WASD + мышь), без needs/AI.
- `MainScene` — создаёт `Player`, ведёт камеру/FOV-конус.
- `GameService` (Angular) — читает Phaser-сцену, отдаёт данные в UI, поллинг раз в 100мс (уже есть паттерн для debug-panel).

Вывод: `Entity` — правильное место для общего фундамента, но здоровье/статы нужны не только `Player`-ветке, поэтому делаем их отдельными **компонентами** (composition), а не через наследование — так `NPCEntity`/животные смогут подключить то же самое позже без переписывания.

## Подход

### 1. Stats — компонент, не часть Entity

Отдельный класс со стартовыми (base) значениями + списком модификаторов (источник → тип статы → flat/множитель → значение). Эффективное значение считается на лету: база + сумма flat-модификаторов, затем умножение на множители.

Почему так: скиллы и травмы должны уметь влиять на одну и ту же стату одновременно, не конфликтуя и не перезаписывая друг друга. Модификатор хранит `sourceId`, поэтому его легко снять целиком (травма зажила / баф закончился) без пересчёта вручную.

Стартовый набор стат: скорость передвижения, дальность обзора, точность стрельбы. Больше стат добавляются простым расширением enum — остальной механизм не меняется.

### 2. Тело — дерево частей на основе шаблона (data-driven)

Части тела не хардкодятся в коде логики — описываются как данные (шаблон/план тела): тип части, родитель, максимальное здоровье, флаг «жизненно важная», коэффициент кровотечения. Из шаблона на старте персонажа строится дерево runtime-объектов с текущим здоровьem.

Почему так: у людей и животных разные схемы тела (у второго может не быть рук, зато четыре ноги). Если план тела — просто данные, для животных позже достаточно завести отдельный шаблон, не трогая логику урона/смерти/кровотечения.

Стартовый план тела (человек): Туловище (корень) → Шея → Голова → {Мозг, Левый глаз, Правый глаз}; Туловище → Сердце, Левая/Правая рука, Левая/Правая нога.

### 3. Обработка урона и последствия — отдельные декларативные правила

Компонент здоровья хранит дерево частей + общий уровень крови (0–100). При уроне по конкретной части:
1. Часть теряет здоровье, при 0 — помечается уничтоженной.
2. Если уничтоженная часть жизненно важная (мозг, сердце) — мгновенная смерть.
3. Пересчитывается суммарная скорость кровотечения (по всем повреждённым частям с ненулевым коэффициентом кровотечения, шея/горло — высокий коэффициент). Кровь тратится каждый тик; при 0 — смерть от кровопотери.
4. Пересчитываются стат-модификаторы от травм по декларативной таблице «часть тела → правило» (оба глаза уничтожены — не осталось обзора, один — обзор сильно хуже; аналогично руки → точность, ноги → скорость). Пересчёт полный (не инкрементальный) — проще и без риска рассинхронизации модификаторов.

Правила урона живут отдельным модулем-таблицей, не внутри самого компонента здоровья — добавление нового правила не требует трогать логику дерева/кровотечения.

### 4. Character — базовый класс только для управляемых игроком/AI-людей персонажей

Новый `Character extends Entity`, добавляет `stats` и `health` как поля-компоненты, плюс тик здоровья (кровотечение, смерть) на каждый `update`. `Player` теперь наследуется от `Character`, а не от `Entity` напрямую. `NPCEntity`/животные не трогаем — они остаются отдельной веткой; если понадобится здоровье животным, компоненты `Stats`/`Health` подключаются к ним напрямую без изменения `Character`.

### 5. UI — окно персонажа

Отдельная Angular-панель (не смешиваем с существующей NPC debug-панелью): текущие эффективные статы, список частей тела с состоянием (% здоровья / уничтожена), уровень крови. Данные идут через уже существующий паттерн поллинга `GameService`. Для проверки без оружия — debug-кнопка «нанести урон N» на каждую часть тела.
